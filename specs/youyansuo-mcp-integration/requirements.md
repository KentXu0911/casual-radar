# 游研所 MCP 与自动更新工作流需求

## 审计范围

本需求覆盖看板的每日指标更新、每周完整更新、候选新品发现、在研产品动态、失败回滚、报告与发布边界。审计基线为当前项目中的 `scripts/daily-refresh.mjs`、`scripts/weekly-refresh.mjs`、共享刷新库、现有 Codex 定时任务以及 `public/games.json` 等公开数据文件。

## 当前已确认的问题

1. 游研所 MCP 尚未进入每日或每周自动任务；现有自动化只调用 DataBrain 指标、事件、研究、GRP 和异动归因流程。
2. 现有游研所扫描脚本是固定日期的公开网页回放 POC，不是授权 MCP 客户端，也没有共享锁、重试、授权错误分类、候选报告或周更回滚接入。
3. 每日/每周脚本依赖 Codex 任务提示检查 Git 是否干净，但脚本自身没有代码级 dirty-worktree 门禁；手工运行仍可能修改用户未提交的文件。
4. 每周流程中的事件、GRP、异动归因脚本直接写入 `public/`，当前回滚依赖 `protectedFiles` 清单完整，新增输出若未加入清单可能在失败后残留。
5. 新产品的指标为空是当前数据契约允许的状态，但 MCP 发现不应因此被伪装成已有 DAU、MAU、收入或趋势数据。
6. 当前运行报告可以记录失败和回滚，但没有独立的 MCP 授权状态、批次覆盖率、候选数量和告警状态。
7. dry-run 会更新 `reports/*-refresh-latest.json` 和历史报告；它能够规划批次，但并非完全无副作用。

## 用户故事

### 1. 作为看板维护者，我希望每日获得游研所扫描结果

这样可以及时发现新产品、榜单变化、公众号新品报道和已跟踪产品的开发动态，而不影响每日指标快照。

### 2. 作为编辑，我希望新产品先进入候选队列

这样我可以核对产品身份、平台、品类、发行主体和来源，再决定是否进入主追踪池。

### 3. 作为产品分析者，我希望已跟踪产品的游研所内容能进入产品时间线

这样公众号原文和在研开发动态可以补充 DataBrain 指标，但不会被误标为上线、版本或运营事件。

### 4. 作为维护者，我希望 MCP 失败时看板保持上一个正常版本

这样授权过期、`internal_only`、超时或部分批次失败不会污染现有数据或阻塞其他已验证数据的回滚。

### 5. 作为审阅者，我希望能分辨数据是否完整、是否已授权、是否已发布

这样本地刷新成功、测试通过、在线部署成功和 MCP 扫描成功不会被混成一个状态。

## 功能需求

### R1. MCP 发现扫描

当游研所 MCP 授权有效且发现任务触发时，系统应按配置的扫描范围调用榜单、文章/公众号、产品目录、发行商产品和开发动态能力，并保存原始响应的不可公开引用信息与规范化结果。

系统不得把 MCP 扫描结果写入 `games[]`、DataBrain 指标或主追踪池，除非经过候选晋级流程。

### R2. 候选新品队列

当扫描结果命中 `public/games.json` 之外的产品时，系统应生成包含规范名称、别名、平台、品类、发行主体、首个发现日期、来源 URL、证据类型、身份置信度和人工状态的候选记录。

候选记录应至少区分：`待核验`、`已确认候选`、`已晋级`、`已驳回` 和 `身份冲突`。

### R3. 已跟踪产品动态

当 MCP 内容能唯一匹配已跟踪产品且有明确发布日期和来源 URL 时，系统应将其作为产品资料或开发动态写入独立的规范化数据集，并允许看板时间线展示。

没有明确实际发生日期的内容不得自动标记为版本、上线、测试或赛季事件；只有文章发布日期的内容应保持研究/报道类型。

### R4. 身份与去重

当产品使用中文名、英文名、代号或地区条目返回时，系统应复用现有统一实体与 `aliases` 映射；无法唯一匹配、标题包含其他产品名或跨地区条目可能重复时，系统应进入人工核验而不是自动合并。

### R5. 指标边界

当候选产品没有 DataBrain 指标覆盖时，系统应保留指标缺失状态并显示来源覆盖说明，不得用 MCP 文章热度、榜单排名或推断值填充 DAU、MAU、收入、ACU 或趋势。

当候选产品通过人工晋级且需要进入指标查询清单时，系统应单独记录该变更，并在后续 DataBrain 批次中验证是否实际返回数据。

### R6. 刷新安全

当每日、每周或 MCP 发现任务开始时，系统应在代码层检查共享锁和 Git 工作区状态；若存在任务开始前的未提交变更，应在任何公开数据写入前停止并列出文件。

当任意 MCP 批次、规范化、校验、测试或构建失败时，系统应恢复本次运行前的公开数据、候选报告和受控输出，不得留下未纳入事务清单的半成品。

### R7. 授权与错误状态

当 MCP 返回 `internal_only`、未授权、OAuth 过期、超时或限流时，系统应分别记录机器可读的错误类别和建议动作；`internal_only` 应提示用户回到游研所网站确认审核状态，而不是被当成空结果。

当一次扫描只有部分批次成功时，系统应将任务标记为 `partial`，保留上一版正式候选集，并把成功批次和失败批次分开记录。

### R8. 报告与发布

当一次刷新结束时，报告应分别记录指标刷新、MCP 扫描、候选晋级、测试、构建和在线发布状态，以及各自的时间、范围、覆盖率和错误。

只有完整校验通过的结果才允许进入发布流程；本地完成、测试通过和 Sites 部署成功必须保持为三个独立状态。

### R9. 看板展示

当存在新的 MCP 候选或已跟踪产品动态时，看板应在独立的“新品发现/开发动态”区域展示来源、证据日期、产品身份置信度和人工状态。

候选不得以“已在研”“已上线”或具有运营指标的主追踪产品样式展示，除非相应证据已经人工确认。

### R10. dry-run 语义

当执行 dry-run 时，系统应只输出计划和校验结果，不应修改公开数据、受控输出或正式刷新报告；若需要记录计划，应写入明确的临时或诊断位置。

## 运行边界

- 游研所 MCP 用于新品发现、公众号原文、榜单变化、产品身份补充和在研开发动态。
- DataBrain 继续负责 DAU、收入、PC/Steam 指标、趋势和异动归因所需的量化数据。
- 公众号/MCP 证据可以补充时间线和研究资料，但不能替代官方日期或指标源。
- 新品自动发现不等于自动入主池；主池晋级需要编辑确认或明确的晋级规则。
- 本需求不授权自动提交、自动发布或覆盖用户当前未提交的工作。

## 非目标

- 不把游研所 MCP 改造成 DataBrain 指标接口。
- 不在本阶段自动把所有 MCP 发现产品加入 `games.json`。
- 不用榜单排名或文章数量推导收入、DAU、MAU 或产品商业结论。
- 不把公开网页回放 POC 作为生产授权链路。
- 不把一次 MCP 授权成功等同于永久有效；每次运行都要记录授权状态。

## 验收标准

1. 在授权有效时，扫描能生成带批次、日期、来源和身份状态的候选报告，且不修改主追踪池。
2. 对已跟踪产品的唯一匹配报道能进入独立动态数据集，并在看板中显示来源和日期。
3. 对身份冲突、无日期、无 URL、重复地区条目和低可信来源，系统能保留人工核验状态而不自动合并。
4. 模拟 `internal_only`、超时、限流和部分批次失败时，正式公开数据与上一次成功版本一致，报告能说明失败类别和回滚状态。
5. 脏工作区启动任务时，脚本在任何公开写入前停止并列出变更文件。
6. dry-run 不改变正式报告和数据文件。
7. 候选晋级后，DataBrain 查询清单和指标缺失状态有可追溯变化；没有指标时看板仍显示缺失而非估算值。
8. 完整测试、构建、本地完成和在线部署状态在报告中可分别核验。
